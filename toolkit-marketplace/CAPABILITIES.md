# Toolkit: capability checks (Phase 0)

Checked against the mod API that Claude Code **2.1.316** writes (`claude-code.d.ts`, ~23k lines), `claude plugin validate`, and the test kit (`claude plugin test`, 104 tests).
This build was done in a **Linux cloud container**, not on the Windows PC. Anything that needs real Windows (toasts, `clip`, `explorer`, the deep link) is implemented and unit-tested for the exact command line, but is marked **needs Windows smoke test** below.

The `benai-mods/` reference folder was **not present** in the container, so feature logic was written from the spec and the engine's own API/examples. `cache-clock`'s `ttl.py` was re-implemented from its described behaviour (read transcript usage, 1-hour vs 5-minute cache writes).

## Engine rules discovered while building (affect the design)

- One **unmatched** hook per event per plugin: `register.tsx` owns `tool.call`, `turn.start`, `turn.step`, `turn.complete`, `agent.spawn`, `prompt.submit`, `session.start` and calls each feature in a fixed order, each inside `guard()` (a failing feature is logged and skipped).
- `$` may only be passed into **function declarations** across files (the validator follows it), so feature code uses `function` declarations.
- `$.state` atoms can only be read/written in the file that defines them.
- Gating hooks (`tool.call`, `agent.spawn`, `prompt.submit`) have `.catch(next)`: if Toolkit throws, your prompt/tool/agent goes through untouched.
